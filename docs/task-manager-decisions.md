# タスク管理ツール 設計判断ログ

対象期間: 2026-10-19 〜 2026-10-20
用途: `task-manager-spec.md` の各項目が「なぜそうなったか」を記録したもの。
実装中に仕様の解釈で迷った際、ここに立ち返って判断する。

---

## 0. 読み方

各項目は以下の形式で記録している。

- **採用** — 決定した内容
- **却下** — 検討したが採らなかった案と、その理由
- **含意** — その決定が他の部分に及ぼす影響

却下案には「今は不要だが後に必要になりうるもの」が含まれる。
仕様変更の要望が出たとき、まずここを確認すると経緯が分かる。

---

## 1. 利用者の性質（設計の前提）

本人の発言から得られた、設計判断の根拠になる特性。

| 特性 | 設計への反映 |
|---|---|
| 「あれもこれも」で何から手を付けるか分からなくなる | 判断そのものをAIに委譲する構造にした |
| **忙しさに気持ちよくなれるタイプ**。ごちゃついてよい | カレンダーに全部詰め込む方針（§6.2）。混雑を許容 |
| **急にやりたくなることがある** | 落としたタスクは削除せず保留に戻す（§5.4） |
| なるべく楽をしたい。気力があるときにまとめて更新する | 入力項目を3つに絞った（§3.6）。属性はAIが補わず、後から追加 |
| 投げ捨て式で思いつきを放り込みたい | 入力口を1つに統一し、分類はAIが引き受ける（§4.1） |

> 本人の言葉: 「思いついたすべてのことを、秘書のように整理し、簡単にスケジューリングしてくれる、脳の拡張ソフトのようなイメージ」

## 2. 決定事項と経緯

### 2.1 タスクの状態 → 3段階

- **採用**: 未着手 / 進行中 / 完了
- **却下**: 完了チェックのみの2値 — 中断中の項目が見えない
- **却下**: 5段階（待ち・保留を独立させる） — 企業連絡の「返事待ち」やVRChatワールドの「投げている」状態を区別できるが、入力の手間が増える
- **含意**: 「返事待ち」は状態ではなくタグやメモで表現することになる

### 2.2 階層 → 2階層、親は自動算出

- **採用**: 親タスク配下に子タスク。親の状態は子から導出
- **却下**: 完全フラット — 「九州即売会」の進捗が見えない
- **却下**: 親も独立した状態と締切を持つ — 柔軟だが入力が増える
- **含意**: 親に独自の締切を置けない。親の締切が必要な場合は、子として「〆切」項目を作るなどの回避が要る

### 2.3 日付 → 開始日＋締切日＋繰り返し

- **採用**: 期間を持て、繰り返し（習慣）にも対応
- **却下**: 締切日のみ — 「11月中にチェック」のような幅を表現できない
- **採用理由**: 「心理学的な根拠に基づいて『これは習慣で行ったほうが良いから毎週何時からに入れる』という判断をAIに行ってほしい」という要望があったため、繰り返し枠が必須になった
- **含意**: 習慣系（デッサン、Duolingo、語学）はタスクと同じ器に入り、カレンダーに毎日並ぶ

### 2.4 入力項目 → カテゴリ・締切・状態のみ

- **採用**: 最小限の3項目
- **却下**: 所要時間・集中度・場所・心理的抵抗を手入力 — AIの判断精度は上がるが、追加のたびに5項目埋めることになり、追加そのものが面倒になって続かない
- **却下**: 上記をAIが自動推定して付与 — 意図には最も合うが、今回は「楽さ」を優先
- **含意**: AIは所要時間や集中度を知らずに配置を判断する。精度が足りなくなった時点で属性追加を検討する。**この却下案は将来の拡張候補として有力**

### 2.5 ウィジェット → Googleカレンダーの純正ウィジェットを流用

- **判明した制約**: Androidのホーム画面ウィジェットはネイティブアプリ（APK）でないと作れない。Webアプリではホーム画面アイコンまでが限界
- **却下**: Androidアプリを自作（Kotlin + Jetpack Glance） — 完全に思い通りになるが、タスク管理ツールを作るためのタスクが増える
- **却下**: TaskerやKWGTなど既存アプリに中継させる — 自作よりは軽いが、それでも中継層が要る
- **採用**: Google Calendar APIで書き込み、Galaxy純正のカレンダーウィジェットに表示させる。中継アプリもウィジェット自作も不要
- **却下**: ICSフィードを購読させる方式 — 実装は軽いが、Google側の取得間隔が長く数時間〜1日の遅延が出る。習慣枠の入れ替えが頻繁に起きるため、古い予定が表示され続けるのは致命的
- **含意**: データはブラウザ内に閉じず、外部から取得できる場所に持つ必要がある

### 2.6 カレンダー書き込み範囲 → 全部

- **採用**: 確定予定・習慣枠・日々の作業タスク、すべて書き込む
- **却下**: 確定予定のみ / 確定予定＋習慣枠 — 混雑は避けられるが、本人が混雑を許容している
- **補足**: 専用カレンダーを1本分けることで、まとめて非表示にできる逃げ道を確保した
- **追加要望**: 優先度を色で分ける（Googleカレンダーは予定ごとに11色から選択可能）

### 2.7 未消化タスクの再配置 → AIが実行、トリガーは手動

- **採用**: 締切から逆算して空き枠に振り直す。詰まりすぎていれば「落とす」判断も含む
- **却下**: 自動で毎朝走らせる — 本人が「頼んだ時にしましょう」と明示
- **却下**: 何もしない / 単純に翌日へ繰り越す — 押し出された分だけ後ろが詰まる
- **追加要望**: オフの日を「オフ」という予定として入れられるようにしたい（詳細は運用しながら）

### 2.8 落としたタスクの行き先 → 保留に戻す

- **採用**: アイデア置き場に差し戻し、棚卸しで再浮上させる
- **却下**: 完了と同じく消す — 「やらないと決めた」のか「やり忘れた」のか後から分からない
- **却下**: 「やらない」として理由付きで記録 — 記録が増える
- **採用理由**: 本人の言葉「急にやりたくなることもあるので」

### 2.9 画面構成 → 3ペイン／タブ

- **採用**: デスクトップはカレンダー1/2、タスクリスト1/4、チャット1/4。モバイルはタブ切り替え
- **本人の想定**: 「アプリ内は思い付きのメモ書きのように扱いたい」
- **含意**: 3枠で埋まるため、AIからの脇道提案は独立した枠を持てず、チャット欄の内部か脇へのオーバーレイになる

### 2.10 チャット欄の性質 → 投げ捨て式＋個別対話

- **採用**: 基本は入力専用（応答は最小限）。タスクや予定を個別に選択したときのみ対話できる
- **却下**: 常時AIと対話できる — 理想だがツール内からAIを呼ぶ実装が要る
- **却下**: チャット欄を置かず外部のClaudeアプリに任せる — 思いついた瞬間に投げられない

### 2.11 入力の切り分け → AIが全面的に引き受ける（**最重要**）

本人の説明をそのまま引用する。

> 入力は一つで、ぽんぽん投げ入れられるものを想定してます。
> それらをAIがタスクのものと、アイデア、やりたいことなどを切り分けて、
> 対話に入ったときに呼び出したり、他のタスクと接続して合体させたりを行ってほしいです。

- **却下**: 投げたものを全部タスクとして扱う — 実行できない項目が混ざってノイズになる
- **却下**: 「未整理」の受信箱を作り、後から人力で振り分ける（GTD型） — 振り分け作業が発生する
- **採用**: 種別の判定をAIが行い、人間は投げるだけ
- **含意**: 投入と実行の間に時間差があってよい。投げたものが即座にカレンダーに載るとは限らない

### 2.12 接続と合体の挙動（**この道具の核**）

本人が挙げた具体例。

```
「ワールドを作りたい」             → ぼんやりした願望
「HDAがたまたまできた」            → 偶然の産物（アイデア／日記）
「再来週に交流会イベントがある」    → 確定した予定
          ↓
AI: 「では再来週までにHDAでワールドを作りませんか？」
```

- **構造**: 日付を持つものが投入されたときが照合のトリガー。そこに差し込める素材が手持ちにあるかをAIが照合する
- **含意**: 単なる整理ではなく、組み合わせによる生成。種別（願望／アイデア／予定／タスク）はこの照合のために必要

### 2.13 眠っている項目の再浮上 → 棚卸し＋文脈連動の複合

- **採用**: 週次などの棚卸しでまとめて提示し、加えて関連作業中に自動で浮上させる
- **却下**: 呼び出したときだけ出す — 死蔵されやすい
- **本人の意図**: 「記憶のストレージとしても機能させておきたい」

### 2.14 外部情報の持ち込み

- **要望**: 「Houdiniの自分の知らない機能を検索して使えそうなものをピックアップする」
- **性質**: 2.13がツール内の再提示であるのに対し、これは外部から情報を取得して既存タスクに接続する動き
- **含意**: Web検索を伴うためツール単体では完結しない。Claude側が調べて提案し、ツールは受け取って保持する

### 2.15 提案のタイミング → 随時＋画面端の吹き出し

- **採用**: 対話中に随時差し込む。加えて画面端に吹き出しでピックアップ表示
- **本人の言葉**: 「本題の対話のチャットの横に使えそうな横道を画面端に吹き出しのような表示で」
- **検討した副作用**: 作業中に別の提案が入ると、そちらに逸れて元の作業が止まる可能性。吹き出し表示はこれを緩和する狙い

### 2.16 フォルダとタグ → 二軸

- **採用**: フォルダ＝領域（就活／サークル／制作／学習／生活）、タグ＝種別その他
- **却下**: 種別だけでフォルダを切る — 「Houdini関連」をまとめて見たいときに散らばる
- **却下**: 領域だけで切る — 種別を表現できない
- **追加要望**: タグの生成も自動化する
- **タグの乱立対策**: 既存タグを優先して再利用し、定期的なリファクタリングで近接タグを統合する
  - **却下**: タグ総数に上限を設ける — 本人が「定期的にリファクタリングさせます」と回答

### 2.17 締切のないタスク → 締切を付けず、接続待ちの素材として寝かせる

当初は「締切なしのものは締切ありに押し負けて一年進まないのでは」という懸念から、
タイムブロッキングや仮の締切設定を提案したが、本人の意図は異なっていた。

> 締切のないタスクをどう進めるかは、締め切りのないまま、階層フォルダの大きいところに放置でいいという意味です。

本人が挙げた例。

```
やりたいこと
  デッサン                                   ← 締切なし。放置でよい
    「石膏像の貸し出しが冬休みに申請可能」   ← 日記として投入
                    ↓
AI: 「冬休みに入ったら、まず申請をしませんか？」
```

- **採用**: 締切を付けない。上階層に置き、日付を持つ情報が来たときに掘り出される
- **却下**: タイムブロッキングで専用枠を確保 / 仮の締切を設定
- **含意**: 2.12の核となる挙動が、締切なしタスクにもそのまま適用される。別枠の進め方は不要

### 2.18 開発方針 → アジャイル

- 吹き出しのレイアウト、リファクタリングの間隔、GUIの細部は事前に決めず、作りながら調整する
- 本人の言葉:「リファクタリングやGUIの見た目は作りながら実行していきます」

## 3. 実装時に注意すべき点

1. **データの置き場所** — Googleカレンダー連携とウィジェット表示のため、ブラウザ内ストレージのみに閉じない
2. **親の締切** — 2階層で親の状態を自動算出する設計のため、親に独自の締切を持たせられない。九州即売会のような親項目で締切が必要になった場合の回避策を用意しておく
3. **属性の欠如** — AIは所要時間・集中度・場所を知らない状態で配置を判断する。提案の質が足りない場合、2.4の却下案（AIによる自動推定）が最初の拡張候補
4. **吹き出しの置き場** — 3ペインで画面が埋まっているため、独立した枠を取れない
5. **種別の推定精度** — 2.11と2.12の全体がAIの種別判定に依存する。ここが外れると照合も提案も機能しない
